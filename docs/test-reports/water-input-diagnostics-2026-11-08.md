## Method

Each case starts a separate browser process and fresh context, opens an isolated copy of the unchanged `index.html` over `file://`, keeps networking offline and the application's CSP unchanged, and loads the same invented sample first. No real survey data or user's browser profile/clipboard is used.

The two ASCII fixtures have 2,050 rows / 82,997 bytes and 25,000 rows / 1,038,947 bytes. Strings, byte counts and SHA-256 hashes are recorded. Each successfully reviewed row is designed to produce four errors and one warning; the maximum input therefore has 100,000 errors and 25,000 warnings. These deliberately invalid invented coordinates are not real locations.

The first matrix compares four routes at 320 CSS pixels for both sizes: native file-picker import with the paste panel closed; opening that populated panel afterward through its summary toggle; direct value assignment followed by one synthetic input event; and Playwright `locator.fill`. Phases distinguish loading, assigning/inserting, input dispatch, two animation frames, Review, value/count verification, scrolling, screenshots and cleanup. Frame waits are responsiveness probes, not a calibrated pixel-paint measurement.

The second matrix uses the maximum fixture, 320 and 1280 CSS pixels, three repeats and two paired arms, interleaved by repeat and width. Identical initialization captures exactly one original app input callback, then restores the listener-registration function. The control removes only that callback from the **original textarea**, preserving native editor state; it does not clone the node. Both arms retain identical diagnostic event observers. This intentional in-page control is not a proposed runtime implementation and must not be used to bypass the app's stale-result invalidation in normal use.

Progress and bounded event metadata are written by Node outside the renderer. Capture/bubble input observers record event types and trust flags; trust flags do not mean physical paste. Detailed events are capped at 20, with constant-space totals available on completed second-matrix cases. Final event totals and in-page measurements may be unavailable on timeouts, so absent observations are not proof that no underlying event ever occurred.

Each case has a 40-second external watchdog. Linux process ancestry and process start times track detached browser descendants, with termination and cleanup checks; only this experiment's child processes are targeted. The total budget is 420 seconds per browser. Setup, missing-report, tracking, cleanup and budget-skip problems fail the diagnostic job. Measured-path timeouts remain explicit findings. All observed timeouts returned through Playwright's 30-second timeout; the external watchdog did not need to fire in these browser cases. Separate synthetic process tests exercise direct and detached-child watchdog termination.

## Results

**Initial Chromium:** Seven of eight cases completed. At 25,000 rows, file import/review completed in 0.440 seconds, reopening the populated textarea completed its toggle/open/frame phases in about 0.413 seconds, and direct assignment plus synthetic input, frame wait and Review completed in about 0.731 seconds. These are measured automation-phase durations on this runner, not end-user guarantees. The smaller fill completed in 6.882 seconds; the larger fill hit the 30-second timeout before Review. Its failure screenshot also timed out after the separate one-second capture budget. The diagnostic listener observed `beforeinput` with `insertText`, but no following input event was recorded before termination. In this first matrix the input observer ran after the app callback, so it alone could not locate the stall relative to that callback.

**Initial Firefox:** All eight cases completed with expected values and counts. The maximum fill RPC returned in 0.373 seconds, followed by 2.404 seconds in the two-animation-frame phase and 0.800 seconds in Review. A fast returned fill call is not equivalent to rendered readiness.

**Repeated Chromium:** All 12 maximum-fill cases timed out at 30 seconds: all three repeats at each width, with the normal callback and with only that callback removed. Each recorded `beforeinput` / `insertText`; neither capture nor bubble input observers recorded a subsequent input event before termination. The node was preserved, exactly one callback was captured, and exactly one was removed only in the control. Removing the app input callback and widening the viewport did **not resolve this observed timeout**. Timeout durations are censored observations, so they cannot establish equal performance or prove the callback has no effect in other situations.

**Repeated Firefox:** All 12 cases completed, each observing one `beforeinput`, one capture-phase input and one bubble-phase input, with `insertCompositionText`. Fill RPC durations ranged from 0.318 to 0.374 seconds; the following two-animation-frame phase took 2.076–2.214 seconds. The repeated checks establish only narrow reproducibility in these environments, not a broad benchmark.

The evidence narrows the reproducible stall to the tested Chromium automated insertion route. It does not isolate the browser/editor/automation internals, establish a universal browser defect, or predict physical clipboard paste, which can use a different event path. It does not justify changing the application's input handler, parser, data limits or paste behavior merely to make this automation pass. No runtime change was made.
